# 07 状态流转与业务规则

[返回总目录](README.md)｜[通用约定](00-通用约定.md)｜[需求覆盖](08-需求覆盖表.md)

本章补充单个请求无法表达的约束。前端按钮只帮助用户操作，后端必须再次校验身份、归属、版本、状态和关联数据。未在状态表允许的操作返回 STATE_CONFLICT；找不到或不属于操作者的私人资源统一 RESOURCE_NOT_FOUND。

## 1 角色、资源归属与隐私

| 身份 | 能做什么 |
| --- | --- |
| 游客 | 浏览审核通过的公开宠物、有效领养需求、公开社区、上架商品；初始化会话、注册登录 |
| 普通登录用户 | 管理自己的资料、收藏、通知、发布、申请、内容、购物车、地址、订单及反馈 |
| 宠物发布者 | 查看本人宠物收到的申请及申请人提交的条件，审核申请、预约、确认交接 |
| 申请人 | 查看本人申请、确认继续领养、撤回或取消符合条件的流程 |
| 管理员 | 在管理员允许的管理接口内工作，不能越过私人日记或私信的边界 |

所有 ownerId、authorId、buyerId、reporterId 从会话取，不接受前端冒用。路径携带 ID 并不意味着有操作权限。涉及两方的详情只允许真实参与人。申请人的 housing、experience、contactPhone 只向双方和 ADMIN 管理员返回，不能放进公开宠物详情。

PRIVATE 日记及其评论仅作者可读，作者可为自己的日记添加评论；禁止收藏、举报或分享私人日记，点赞仅作者自己可设置。本人收藏过的公开内容转私密后，收藏列表只显示不可用占位。管理员公开内容接口不能查看私人日记；日志不保留私人正文。私信没有管理员浏览接口，投诉只引用申请和提交者说明，不授权管理员读取私信。

普通用户冻结后不能再登录，现有会话立即撤销。原公开内容保持原审核状态；需要下架时由相应管理接口操作，避免冻结同时隐式取消所有历史业务。

## 2 宠物发布和审核

reviewStatus 表示发布审核，adoptionStatus 表示领养，两者不能混为一个状态。

| 操作 | 前置 | 结果 |
| --- | --- | --- |
| 创建草稿 | 登录用户 | DRAFT + AVAILABLE |
| 修改资料 | 本人，DRAFT/REJECTED/OFF_SHELF，且 AVAILABLE | DRAFT，版本增加 |
| 提交审核 | 本人，同上，至少一张 PET 图片且档案完整 | PENDING |
| 管理员同意 | ADMIN，PENDING | PUBLISHED |
| 管理员拒绝 | ADMIN，PENDING | REJECTED，记录说明 |
| 本人下架 | DRAFT/PENDING/PUBLISHED/REJECTED，无预留或交接中申请 | OFF_SHELF，待审核申请全部 CANCELLED |
| 管理员下架 | ADMIN，非 OFF_SHELF | OFF_SHELF，联动取消未完成申请及未结束预约 |

只有 PUBLISHED 的宠物可公开浏览，AVAILABLE 才能接收新申请。ADOPTED 可以展示领养完成结果，但不得重新申请或修改成未领养。宠物公开详情不返回申请人身份、联系方式和审核内部说明。

管理员下架时，若原宠物为 RESERVED，其唯一有效申请由 APPROVED/IN_PROGRESS 转 CANCELLED，宠物变 AVAILABLE，但仍 OFF_SHELF；如果已经 ADOPTED，保留 ADOPTED 和完成记录。

## 3 领养申请与交接

| 当前状态 | 允许动作与操作者 | 下一状态及关联变化 |
| --- | --- | --- |
| 无申请 | 申请人提交，不得申请自己的宠物 | PENDING；同一人同宠物不能有多个有效申请 |
| PENDING | 申请人撤回 | WITHDRAWN |
| PENDING | 宠物发布者拒绝 | REJECTED，说明原因 |
| PENDING | 宠物发布者同意并选定此人 | APPROVED；宠物 AVAILABLE→RESERVED；其余 PENDING 申请 REJECTED |
| APPROVED | 该申请人确认继续领养 | IN_PROGRESS |
| IN_PROGRESS | 该宠物发布者确认交接完成 | COMPLETED；宠物 RESERVED→ADOPTED |
| APPROVED / IN_PROGRESS | 任一方取消 | CANCELLED；宠物恢复 AVAILABLE；未结束预约取消 |
| PENDING / APPROVED / IN_PROGRESS | ADMIN 管理员异常取消，或宠物被管理员下架 | CANCELLED；必要时释放宠物并取消预约 |
| COMPLETED / REJECTED / WITHDRAWN / CANCELLED | 历史查询 | 终态，不允许直接恢复或删除历史 |

发布者同意申请就是选定最终候选领养人；申请人随后确认，发布者在完成线下交接后确认完成。界面应展示每一步操作者，不把“申请被同意”当成领养已经完成。历史拒绝或取消申请不自动恢复为待审核，用户可在宠物再次开放时新建申请。

同意申请、宠物状态变更、拒绝其他申请及相关通知必须处于同一个事务。以宠物为锁定中心保证同一宠物同时只有一条 APPROVED/IN_PROGRESS 或完成关系。发布者审核时须再次确认宠物 PUBLISHED+AVAILABLE，防止并发选择两人。

时间线在每次申请状态变更时记录 status、时间、用户可见说明；不得在面向申请人的时间线泄漏其他申请人的条件或联系方式。完成记录即状态 COMPLETED 的申请，不另建一套能独立修改的“领养成功”接口。

## 4 领养需求与匹配

| 状态 | 变化 |
| --- | --- |
| ACTIVE | 有效期内可编辑，超过截止时间变 EXPIRED，本人或管理员可关闭 |
| EXPIRED | 不公开展示，仅本人/管理员查询，可关闭为 CLOSED |
| CLOSED | 终态，不恢复；有新需求重新发布 |

每个用户最多 3 条有效 ACTIVE 需求；expiresAt 必须晚于提交时间，最多 180 天；minAgeMonths ≤ maxAgeMonths。请求读取时也要判断有效期，不能只依赖定时任务已经运行。

推荐仅包含 PUBLISHED+AVAILABLE 的宠物；种类相同 40 分、月龄在范围内 20 分、所在地完整字符串相同 20 分、性别相同或偏好 ANY 20 分。种类不同时仍可得其他项分，本版按总分列出候选并说明命中项；无需模型训练。分数降序后按宠物 ID 降序，未命中项不得编造匹配理由。仅本人有效需求可请求推荐；已过期或关闭返回 STATE_CONFLICT。

## 5 私信与预约

会话唯一维度是「宠物 + 两位参与人」，不能创建自己给自己的会话。会话创建时另一方必须是宠物发布者；宠物未公开时必须双方已有申请。会话一旦建立，宠物下架或领养结束不抹除已有沟通，但冻结账号不能继续访问。

私信为纯文本；clientMessageId 在发送者维度唯一，同 UUID 同会话同内容重试返回同条消息，不同会话或内容返回 IDEMPOTENCY_CONFLICT。先写消息再更新摘要与未读数，采用同事务。已读位置只能前移且必须属于当前会话，不能通过提交其他会话 ID 清除未读。

消息列表按 ID 降序分页；Vue 展示时按 ID 排序并去重。新消息轮询第 1 页，以最后收到的 ID 判断新增；若当前页全为新消息，继续读取后续页直到已知 ID，避免高频消息漏读。不要求 WebSocket。

| 预约状态 | 操作 | 下一状态 |
| --- | --- | --- |
| 无预约 | APPROVED 或 IN_PROGRESS 申请的一方提出 | REQUESTED |
| REQUESTED | 非创建方确认，且开始时间未过 | CONFIRMED |
| REQUESTED / CONFIRMED | 任一方取消，或领养流程取消 | CANCELLED |
| CONFIRMED | 预约结束时间已到，任一方确认 | COMPLETED |

startsAt < endsAt，创建时 startsAt 为未来，单次最多 4 小时。按 `[startsAt,endsAt)` 判断时间是否冲突，同一人任意宠物的 REQUESTED/CONFIRMED 不得重叠。创建、确认时按固定用户 ID 顺序锁定两名参与人再检查冲突，不能只在前端判断。过期未确认请求读取时自动取消；已完成预约保留历史。

## 6 社区内容、审核与互动

kind 固定为 POST（交流帖子）、DIARY（日记）、HELP（求助），创建后不可改种类；只有 DIARY 允许 visibility=PRIVATE。DIARY 的 petName 必填，暂不要求关联已发布领养宠物，让没有领养发布记录的用户也能记录自己的宠物。

| 操作 | 当前情况 | 结果 |
| --- | --- | --- |
| 新建 | 任意类型、合法可见范围 | DRAFT |
| 提交公开内容 | DRAFT / REJECTED / OFF_SHELF | PENDING |
| 审核同意/拒绝 | PUBLIC + PENDING | PUBLISHED / REJECTED |
| 编辑公开已发布内容 | PUBLIC + PUBLISHED | PENDING；修改内容暂不公开，等待重新审核 |
| 编辑其他公开内容 | DRAFT / PENDING / REJECTED / OFF_SHELF | DRAFT；重新点击提交才送审 |
| 提交私人日记，或保存私人日记修改 | PRIVATE 日记 | PUBLISHED，仅本人可见，不走管理员审核 |
| 公开日记改成私人 | 任意非删除状态 | PRIVATE + PUBLISHED，立即对其他人隐藏 |
| 私人日记改成公开 | 原 PRIVATE | PUBLIC + PENDING |
| 管理员下架 | PUBLIC 非 OFF_SHELF | OFF_SHELF，保留作者修改与删除能力 |
| 作者删除 | 任意非删除状态 | 逻辑删除，所有正文详情与媒体停止访问 |

社区正文最大 10000 字、标题最大 100 字、最多 5 个去重标签、9 个文件。分类必须存在且新绑定时启用。已绑定分类停用后，原内容仍可展示；保留原分类编辑其他字段不要求换类，主动换类必须选择启用项。私密转公开时所有媒体权限随资源状态变化，审核通过前仍不可匿名读。

公开内容只有 PUBLIC+PUBLISHED 时支持新增评论、回复、点赞、收藏及分享。帖子下架后不得靠旧评论地址绕过访问检查。用户只能修改或删除本人评论；文章作者没有删除其他用户评论的权力，可举报。评论修改不走人工逐条审核，可被举报后移除。

评论仅一层回复：parentId 为空是顶级评论；回复任意一条回复时归入对应顶级评论。请求父评论需属于同一帖子且未删除。删除有回复的父评论保留固定“该评论已删除”占位，不返回原文，原作者 ID 和昵称也使用空占位值；由此 Comment.authorId 允许空字符串。没有回复的删除评论可不出现在用户列表，管理列表仍返回占位。commentCount 统计未删除的评论与回复。

点赞、收藏使用 userId+targetId 唯一约束，同一个用户重复操作不重复增减。点赞或评论数量变化不改变内容编辑 version，正文和审核状态变化才改变 version，避免互动导致作者无法保存。私密日记转公开及相反转换不复用旧的匿名媒体缓存。

举报可针对 POST 或 COMMENT，但必须当前用户可访问且为公开内容。处理举报仅反馈结果；下架帖子或移除评论分别调用有对应权限的管理接口，以便记录独立的原因与操作日志。

## 7 商品、购物车和地址

一个商品在本版对应一个可售单位，不设计规格/SKU、多商家、优惠券和购物券。单价至少 1 分，库存为 0–1000000。新增商品 OFF_SHELF；上架要求分类启用且资料完整。商品图片使用 PRODUCT 媒体。

购物车以 userId+productId 唯一，PUT 设置最终数量，不做模糊“加一”。界面增加数量前先算新值再 PUT。每项 1–99；加入不占库存，展示当前价格；下架或分类停用后保留但标 available=false，不能结算。

每用户最多 20 条地址。首条自动默认；存在地址时必须恰好一个默认。创建或修改 isDefault=true、单独设置默认，以及删除默认地址都在用户维度加锁并事务处理。修改当前唯一默认地址时传 false 且没有其他默认候选，返回 VALIDATION_ERROR；应通过设置其他默认地址切换。订单持有地址快照，不随地址编辑或删除改变。

## 8 购买、订单与取消

结算顺序：前端选择商品数量和本人地址 → POST preview 试算 → 展示总额 → 用户点击购买 → POST orders → 返回购买成功。创建订单同时记录 paidAt 与 paymentMode=MOCK，初始 WAIT_SHIPMENT；不出现待支付页，不调用外部支付，不发送支付回调。

items 商品 ID 不得重复。服务端核对商品上架、分类启用、库存充足和地址归属，再根据当时单价计算总额。expectedTotalCents 只是用户确认值，不是可信价格；总额不一致返回 PRICE_CHANGED，前端重新试算并请用户确认。一次最多 50 个不同商品，运费固定 0，总额不得超过 money 模型上限。

cartItemIds=[] 表示直接购买；非空时，必须为当前用户选中的购物车行，且与 items 的商品集合及数量逐一完全一致。只清除本次选中且与试算一致的行，不影响购物车其他商品。购买同事务按商品 ID 升序锁定库存，使用条件扣减，写入不可变商品和地址快照，并在订单行保存模拟付款结果。任何条目库存不足均整体失败，不产生半张订单。

| 当前订单状态 | 操作者与动作 | 下一状态及库存变化 |
| --- | --- | --- |
| 无订单 | 用户模拟购买成功 | WAIT_SHIPMENT；库存扣减一次 |
| WAIT_SHIPMENT | 买家或 ADMIN 管理员取消 | CANCELLED；库存恢复一次，记录全额模拟退款成功 |
| WAIT_SHIPMENT | ADMIN 管理员填写发货 | SHIPPED；不再次扣库存 |
| SHIPPED | 买家确认收货 | COMPLETED |
| SHIPPED / COMPLETED | 买家申请整单退款 | REFUNDING；先不恢复库存 |
| REFUNDING | 管理员同意模拟退款 | REFUNDED；是否恢复库存由收货核实决定 |
| REFUNDING | 管理员拒绝 | 恢复申请前的 SHIPPED / COMPLETED |
| CANCELLED / REFUNDED | 查询历史 | 终态 |

取消和发货都锁同一订单，竞争只允许一个成功。已发货不能走“取消未发货”接口。取消退款结果直接由订单 CANCELLED 表示，不额外创建 Refund 申请；Refund 列表专门展示发货后的退款申请。物流只展示人工填写的公司、单号和发货状态，不接轨迹服务。

## 9 模拟退款

仅整单退款；申请金额取订单全额，客户端不传金额。REQUESTED 表示待管理员处理；同意时同事务记录 APPROVED→SUCCESS，外部查询成功后直接看到 SUCCESS；APPROVED 是过程记录，不引入后台支付任务。拒绝为 REJECTED。

订单同一时间只能有一个 REQUESTED 或已成功退款。已拒绝且订单恢复原状态后可重新提交。审核同意时订单变 REFUNDED、退款 SUCCESS，且 restock=true 只有在管理员确认商品已经收回才允许。退款不默认等于商品已退回；restock=false 仍可退款但不恢复库存。审核拒绝时 restock 必须 false。

退款、取消恢复库存与人工补货一样会增加商品 version。恢复库存不得超过库存上限，异常时整笔事务失败，由管理员先核对库存。所有动作使用幂等键及订单状态锁，重复请求不重复退库存。钱款处理均为站内状态模拟，不表示任何真实资金流动。

## 10 管理员身份及保护

普通用户为 USER，管理员为 ADMIN。所有管理业务统一检查 ACTIVE+ADMIN；不提供自定义角色、权限字典和逐项授权。管理员仍受私人日记、私信隐私及业务状态限制。用户端必须校验资源归属。

不能冻结自己；最后一名 ACTIVE 管理员不能被降为 USER 或冻结。变更管理员身份时按用户 ID 顺序锁定有效管理员行，重新统计并检查版本，避免并发同时移除最后两名管理员。身份变更递增 auth_version，目标原会话失效。首名管理员需由项目负责人在受控初始化流程设置；没有默认管理员密码，当前管理员业务尚未开发。

## 11 通知、举报与投诉

| 触发动作 | 接收人 | businessType |
| --- | --- | --- |
| 新领养申请 | 宠物发布者 | ADOPTION |
| 同意/拒绝/撤回/取消/确认继续/完成领养 | 申请相关另一方；批量拒绝各申请人 | ADOPTION |
| 宠物审核或下架、需求被关闭 | 发布者；影响中的申请人另发进度通知 | ADOPTION |
| 预约创建/确认/取消/完成 | 另一参与人 | ADOPTION |
| 社区审核拒绝/同意/下架、违规评论被移除 | 内容作者 | COMMENT |
| 新评论或回复 | 帖子作者或被回复评论作者；去重，不给自己发 | COMMENT |
| 购买成功/发货/取消/确认收货 | 买家 | ORDER |
| 退款处理成功/拒绝 | 买家 | REFUND |
| 举报处理完成 | 举报人 | REPORT |
| 领养投诉处理完成 | 投诉人 | ADOPTION |
| 管理员平台通知 | ALL 当前有效用户或 USERS 指定账号 | SYSTEM |

通知与相应业务变更同事务写入，失败应回滚；本版不依赖消息队列。通知正文只写适合接收人的摘要，不附其他用户私密资料。业务内容失效后仍可看通知文字，点击详情仍重新检查资源权限。

举报和投诉均 PENDING→RESOLVED / REJECTED，一旦结案不修改结果；新问题可另提。相同用户、同目标存在 PENDING 时不允许重复。举报管理员只反馈处理结果，下架另需 ADMIN；领养投诉管理员只结案反馈，异常取消另用取消接口。每次处理填写措施或驳回依据，用户可查结果并收到通知。

ALL 平台通知以创建时 ACTIVE 用户快照为收件人，不给未来注册用户自动补发。USERS 必须 1–1000 个存在且 ACTIVE 的用户 ID，ALL 的 userIds 传 []。通知记录保留实际 recipientCount；同幂等键不重复群发。

## 12 日志、事务和实现边界

所有管理写操作记录操作者、动作、对象、原因、结果、requestId、时间；查询不记录为业务操作日志。审核、下架、冻结、重置、发货、退款、库存及角色变更必须可追溯。只有非敏感摘要进入日志，不记录密码、哈希、临时密码、Cookie、CSRF、原始私信或私人日记。密码重置的成功响应仅管理员当前会话可见，保留幂等结果需加密。

管理成功日志随业务事务提交；失败审计在业务回滚后独立落库，只保存安全摘要，不能因为记录失败日志误提交业务修改。错误与审计通过 requestId 关联。操作日志不提供修改或删除接口。

资源 version 只在可编辑字段或业务状态实际变化时增加。收藏、点赞、已读等明确幂等设置未改变结果时不增加版本。关联资源同步变化（申请同意更新宠物、库存改变商品）须增加各自对应 version；客户端后续操作应重新读取。

实现时使用 MySQL 事务、唯一约束、版本条件更新和必要行锁。分页、校验、身份认证、权限、CSRF、统一异常、媒体读取、幂等处理属于共用能力；Controller 接收 DTO，Service 组织流程，Mapper 访问数据库，VO 返回数据。数据库设计见数据库文档，当前为 Spring Boot 单模块。

## 精简版存储规则

- 身份固定为 USER / ADMIN；不再分配自定义角色。注册和资料更新不接受 role。管理端仍保护最后一名有效管理员，角色变更或冻结立即撤销目标会话。
- 领养时间线保存在申请 progress 数组中，最多 100 项，与状态同事务更新；条目 ID 为当前数组序号的十进制字符串，稳定递增。
- 双人会话的两个已读位置直接保存在会话表，未读消息数按位置查询。只接受当前会话的消息 ID，已读位置仅前移。
- 社区 tags 是最多 5 个、每个 1–20 字的去重字符串数组，沿用标签检索功能。
- 模拟购买直接在订单保存 SUCCESS、paid_at；取消／退款成功设置全额 refund_amount_cents 和 refunded_at，与按业务规则执行的库存回补同事务；退款 restock=false 时不回补。只支持整单模拟退款。
- 库存由商品、订单状态及事务保证；订单按关键时间字段显示进度，不单独建库存流水、订单事件或付款表。
- 公告和站内消息共表，以 is_broadcast 区分主记录与收件消息，用户只能查询自己的收件行。
