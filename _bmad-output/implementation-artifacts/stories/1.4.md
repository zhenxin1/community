# Story 1.4 管理员查询与处置用户

状态：review。技术证据已归档，最终人工验收待记录。

## 用户故事
作为平台管理员，我希望准确定位普通账号并作出可解释处置，以便在当前业务阶段得到明确且可验证的处理结果。

## 关联与前置
- 功能需求：FR-04 FR-05。
- 页面入口：`/admin`。
- 前置故事或条件：1.1、1.3。
- 详细业务规则：[PRD](../../planning-artifacts/PRD.md)；技术约束：[架构](../../planning-artifacts/architecture.md)。

## 输入与主流程
本故事接收账号筛选、状态、目标ID、版本、原因和operationId。界面先展示可操作信息与当前状态，提交期间提供处理反馈。Controller只处理请求合同，Service核对身份、对象关系、字段与业务状态，Mapper在统一数据库完成必要读写；页面按实际响应展示结果，不自行伪造成功状态。

### AC-1.4-01
给定上述参与者和相应业务数据，当通过页面或直接请求执行该场景，则：ADMIN可按账号和状态分页查询；USER或游客直接访问后台接口拒绝。

### AC-1.4-02
给定上述参与者和相应业务数据，当通过页面或直接请求执行该场景，则：冻结普通账号后状态、原因、版本和说明通知共同保存，旧会话失效。

### AC-1.4-03
给定上述参与者和相应业务数据，当通过页面或直接请求执行该场景，则：同一命令同载荷重试返回原结果，不新增第二条处置通知；异载荷复用返回冲突。

### AC-1.4-04
给定上述参与者和相应业务数据，当通过页面或直接请求执行该场景，则：解冻必须基于当前版本；完成后旧会话仍失效，管理员自身及其他ADMIN不能作为处置目标。

## 实现与测试任务
1. 页面：展示本故事所需数据、操作与加载/空/错误状态，保护非敏感输入；密码字段不作为重试缓存。
2. Controller：保持统一请求字段及错误语义，拒绝未知或不合法输入，不接受客户端伪造身份。
3. Service与Mapper：复用身份能力，校验归属和状态；相关写入按既定事务及锁序执行。
4. 正向验证：从页面或HTTP完成主流程，核对响应与数据库最终结果。
5. 负向与重复验证：覆盖游客、普通账号越权、非法字段、过期版本或重复操作中与本故事相关的情况。
6. 证据与评审：关联已有自动化结果和页面记录，记录修正；人工接受后再按实际决定更新冲刺状态。

## 验证入口与完成定义
自动化入口为`tests/integration.py`、`tests/quality.py`及后端JUnit。测试名称、实现领域与FR的具体对应见`docs/traceability.md`，实际结果见`evidence/verification.md`。浏览器记录仅代表已执行的页面路径，不替代未执行的场景。
完成应具备可运行页面与接口、权限和异常处理、可核对测试、文档一致及负责人接受；缺少人工接受时保留review，不以技术通过自动变为done。
